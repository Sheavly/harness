# Extending the harness

Each section is the canonical path for one kind of addition. If your change does not fit one, you are probably modifying a core module: stop and find the system that owns the concept ([principles.md](principles.md)).

## A tool

Create `packages/tools/src/<name>/` (generic) or `extensions/coding/src/<name>/` (files or commands), copying the shape of `@sheavly/coding`'s `read-file/`. `defineTool` and the `Tool` types come from `@sheavly/core/tool/tool.utils` / `tool/tool.types` (`runTool` from `tool/tool.helper`).

- `<name>.tool.ts`: `create<Name>Tool(options)` returns `defineTool({ name, description, inputSchema, execute })`.
- `inputSchema` is a `z.object`. Never add a `description` field: the harness adds the model's call description itself and strips it before `execute`.
- `execute({ input, signal, context })` returns a string, or `{ content, artifacts }` to give a UI data the model never sees (tagged with a `kind` the tool owns, e.g. the file tools' `FileChange`: emitted on `tool_result`, never put in history; see `docs/tools.md`, "Artifacts"). It throws `Error`s with clear messages (`runTool` turns them into error results). Pass `signal` to every async operation.
- All file access goes through `Workspace` (`resolveRead` / `resolveWrite`); writing tools use `resolveWritable` from `@sheavly/coding/files/files.helper`. Never read or write `.env*` files. Commands go through the coding extension's own `ProcessRunner` (`@sheavly/process/process/process.service`) and the allow list.
- Include it from the backend that wants it (`createBackendHarness`), with `*.tool` exported by its package (`npm run export -- packages/<pkg> tool`). No package adds a tool to a run.

## A sub-agent

An extension builds the sub-agent tool from scopes, never from registries: `createSubAgentTool({ scopes: { sessions, children, tasks, taskControl }, provider, tools, hooks? })` (`@sheavly/tools/sub-agent/`), where the scopes are the `session-info`, `child-sessions`, `background-tasks` and `task-control` run services the extension declares with their grants ([extensions.md](extensions.md), "Run services and grants"). `children.runChild` owns the call into the loop: the extension never holds a `SessionRegistry`, a `TaskRegistry` or the loop's `runSession`. Every run is a session in a `SessionRegistry` (`@sheavly/runtime/sessions/`), which the app and the loop hold: pass `session: { registry, ref }` to the loop, or it starts its own main session. Sub-agents nest at most `MAX_SESSION_DEPTH` (3), always under a running parent, and report their own status with `report_status`; a parent steers one with `message_agent` (the session inbox, through the `sub-agent:message` grant, delivered at the next model call). The registry's `stream()` is the SSE feed. See `docs/sessions.md`. Every session of a run shares its one `TaskRegistry`: a tool that reads or cancels tasks goes through `TaskControl` and passes the caller's `context.session?.id` (`list`, `getOwned`), and a session's shutdown is `cancelSession` (done by `runChild`), never `cancelAll`. A sub-agent is background work: see [state-machines.md](state-machines.md) for how it and a background command must agree.

## A kind of background work

A tool that runs work in the background does not call `tasks.start`. It builds a `WorkDefinition` with its kind's factory (`finiteWork` / `agentWork` / `serviceWork` from `@sheavly/runtime/tasks/work.utils`, or a kind of its own that wraps one, like `subAgentWork` and `commandTaskWork` / `commandServiceWork`) and starts it with `startWork({ tasks, work })`, where `tasks` is a `TaskStarter` (`{ start(work) }`): the registry for the app, or the `background-tasks` scope (grant `task:start`) for an extension. The factory fixes the completion policy (finite and awaitable, or a service); the caller passes the kind and its inputs, never the policy. A new kind is one factory next to its tool, with a test that pins its policy, and, by review (nothing checks it: the entries are fakes, not the factories), one entry in `WORK_KINDS` (`packages/loop/src/testing/work-kinds.fake.ts`): `flow-kinds.test.ts` then runs it through the shared lifecycle (one notice, one `task_completed` event, release, no growth). `harness/no-direct-task-start` enforces it: it is type-aware and fails any access to `TaskRegistry.start` (a call, an alias, destructuring, `.call`, a string key) in source outside `packages/runtime/src/tasks/work.utils.ts`; tests and fakes are exempt by file kind. It cannot see a registry typed `any`, cast to another shape or assigned to a structural type that re-declares `start`; review carries that.

## A provider

See `packages/providers/docs/backends.md`. A Responses API backend is one folder, `packages/providers/src/<name>/<name>.adapter.ts`, using `defineResponsesAdapter({ kind, description, configSchema, toEndpoint })` (from `responses/responses.helper.ts`): a pure map from config to endpoint. Another protocol (Anthropic, Gemini, Chat Completions) gets its own protocol folder next to `responses/` and backends on it; it never reuses `responses/`. Anything else uses `defineAdapter` (from `@sheavly/core/adapter/adapter.utils`). Register built-ins in `registry/default-registry.helper.ts`. Adapters have no default model; the app that builds the provider picks it. Core code doesn't change. Model calls go out through `createModelFetch()` (`packages/providers/src/http/model-fetch.helper.ts`), never Node's global `fetch`: its TLS ClientHello fits in one TCP segment, which Azure AI Foundry needs on Node 22.20+, 24.5+ and 26. A registry built with no deps uses it. `harness/no-raw-model-fetch` fails a source file that builds `createDefaultRegistry` or `AdapterRegistry` with any other `fetch` written in the call. Tests and fakes pass their own. Deps held in a variable are review-only. Inside `@sheavly/providers`, an adapter or protocol sends through the injected `deps.fetch`: `modelFetchConfinement` (spread into its `eslint.config.js`) fails a source file that calls Node's global `fetch`.

## A loop event

Add its schema to `agentEventBodySchema` in `packages/protocol/src/event/event.validator.ts` (then `npm run schema -w @sheavly/protocol`) and emit it through the `OrderedQueue`, never directly, so `seq` stays contiguous and in causal order. Handle it in the terminal app's `Renderer` (`apps/terminal/src/render/`), whose switch over event types must make an explicit choice to render or ignore each one; presentation belongs to each UI.

An extension never edits the protocol for its own event. It declares the kinds in its manifest (`emits.events`, `<extension>.<name>`), returns `events: [{ kind, version, schema }]` from `activate` and emits through `context.emit.event` (`@sheavly/extension`); the loop event union already has the open `extension_event { extension, kind, version, data, text }` for it. A UI never switches on `kind`: it shows `text` for a kind it does not know. Add a union member only for an event the harness itself sends.

## A route (the HTTP API)

One entry in `API_ROUTES` (`packages/protocol/src/api/api.constants.ts`), named after what it does (`get…`/`list…`/`query…`/`stream…` for a read, a verb for a change), with its body and answer as schemas in `server/server.validator.ts`. Declare its `effect`: `ApiRoute` then allows only the methods that fit, so the typecheck fails a read on `post` or a `get` with a body. A read without input is `get`; a read with input (a filter, a search, a resume point) is `query`, its input a typed body, never a query string; a change is `post`, `put` (setting a value) or `delete`. Then run `npm run schema -w @sheavly/protocol` (a test fails while `openapi.json` is stale, and another holds each route's name and path to these rules), add its handler to the backend's `apiHandlers` (`apps/backend/src/api/handlers.helper.ts`: `ApiHandlers` makes a missing one a type error, and `api.helper.test.ts` fails for a route the app doesn't serve), and call it from a UI with `createClient`, which takes it by name with nothing to add. A route is private (it needs the bearer token, and `createClient` sends it) unless it carries `public: true`; only `getHealth` and `queryHandshake` do (`public-routes.constants.ts`), and a route that answers without a token reveals nothing of the user's data. The backend's `public-routes.test.ts` and the protocol's `api.utils.test.ts` enumerate the public set, so making a route public is a visible change that fails them until the set is edited on purpose; a new route needs no flag and stays private.

## A hook

`defineHook({ name, sessionStart?, beforeTurn?, beforeModelCall?, beforeSummary?, afterSummary?, aroundToolCall?, afterTurn?, taskCompleted?, notice?, approval?, sessionEnd?, onError? })` from `@sheavly/core/hook/hook.utils`, passed in the loop's `hooks` option (order matters).

- `sessionStart` (once per run) and `beforeTurn` add context with `addContext` (a user message kept in history, emitted as `context_added`); `beforeTurn` can also `addInstructions` (system instructions for that model call only, appended to the run's `instructions` option, never in history). Changing the system prompt invalidates Claude's signed thinking prefix: the built-in AGENTS.md and skills hooks append changed instructions with `appendInstructionContext` (`@sheavly/core/instruction-context/instruction-context.helper`), deduplicated from history, rather than replacing system instructions.
- `beforeModelCall` returns the messages to send for that one call (it gets a deep copy and its result is parsed and checked by `assertValidHistory`: tool calls stay paired and the latest user message unchanged, a violation is an `InvalidHistoryError`; stored history never changes, and edits should be deterministic so the prompt prefix stays cacheable).
- `beforeSummary` (only with the loop's `summary` option) may return `{ keepTokens?, sections? }`, parsed by the loop, to move the cut or add sections, and a bad result fails that summary (`summary_failed`), never the run; `afterSummary` gets copies of the new checkpoint and of the view, and adds context back with `addContext` (never copy the checkpoint's text into it: it comes from tool output).
- `aroundToolCall` calls `next()` to continue, or returns a result to block; `afterTurn` sees the turn's reply with tool results in history; `onError` is told when the run fails (the run's error is rethrown; a handler that throws doesn't stop the others and is reported as a `hook_failed` event).
- A new hook point is one name in `HANDLER_NAMES` (`hook.constants.ts`) plus its signature in `HookHandlers` (`hook.types.ts`). `Hook`, `handlerNames` and the project-hook schema derive from that list. Add its runner in `@sheavly/loop/hooks/` and name it in `RUNNERS` in `handler-coverage.test.ts`: the typecheck fails until you do, and the test fails if the runner does not exist.
- `taskCompleted` (finished work delivered) and `notice` (a persistent notice reached history) may `addContext`; `approval` may return an answer the request offers (e.g. `skip_with_message`) to settle a request before any UI hears it; `sessionEnd` runs once before `done`, even after an abort.
- A handler that throws never fails the run: it is a `hook_failed` event and a `hook-failed` notice, and the run goes on without it. `aroundToolCall` and `approval` fail closed.
- A feature of the turn (masking, overflow recovery, output limits) is a contribution in `turn-contributions.helper.ts`, with a name, an `after`, an `onFailure` and an `abort` policy; never an `if (options.x)` in `runTurn`.
- Two hooks, or two tools, with the same name are a collision: never rely on one shadowing the other.

## An instruction source

AGENTS.md, skills, scratch and the working root are instances of one factory, `createInstructionHook` (`@sheavly/core/instruction-context/instruction-source.helper`; the generic mechanism lives in core, the coding sources in `@sheavly/coding`, the scratch one in `@sheavly/workspace`). A new source is one instance:

1. Write `<name>Source(options): InstructionSource` with a unique `name`, an `order` (add it to `INSTRUCTION_ORDER` in `packages/workspace/src/instruction-context/instruction-source.constants.ts`) and `resolve({ signal, workingRoot })`, which returns the text that applies now or `undefined`. Pass `workingRoots` when it depends on the working root: the factory reads it every turn, and its owner makes it return `undefined` instead of throwing when the folder is unusable (`usableWorkingRoot(workingRoots)` in `@sheavly/coding/working-root/usable-working-root.helper` does that for `WorkingRoots`), so a worktree chosen mid-run applies on the next model call.
2. Register `createInstructionHook(source)` with `registerInstructionHooks([...])` in the app (`createBackendHarness`). Hook order comes from each `order`, never from array position; a repeated name throws `InstructionSourceError`.
3. Dedup is the factory's, so a source keeps no state: the last `<instruction-context name="…">` user message in the history the hook is given is compared with the new text, and only a change (or withdrawal) is appended. A summary or masking that drops the entry makes the next turn announce it again; sub-agents announce on their own history. Never replace system instructions: it invalidates Claude's signed thinking prefix.

## A project hook (`.sheavly/`)

Listed in `.sheavly/hooks.json`, loaded by `@sheavly/coding/project-hooks/` with a native `import()`, its default export validated with zod. A new handler is accepted here with no edit: `hookExportSchema` reads its keys from the handler list. Tests write real temp projects; `vitest.config.ts` keeps Vite away from `.sheavly` files so Node's own ESM/CommonJS/TypeScript rules apply. Code from a repo runs only in a trusted workspace (`TrustStore`).

## A notice

A model-facing or UI-facing fact is a `HarnessNotice` kind (`@sheavly/protocol`), written only by `formatHarnessNotice`. Decide its lifetime when you add it: transient (rides one model call, never stored) or persistent (stored in history as a `notice` entry). Add tests for the shared payload, the ordered stream and history isolation.

An extension never edits the protocol for its own notice either. It sets `emits.modelFacingNotices: true` in its manifest, returns `notices: [{ topic, version, schema }]` from `activate` and emits with `context.emit.notice`: the persistent `extension-notice` kind carries it, queued in the session's outbox and published by the loop's `extension-notices` delivery contribution at the next turn. Only its `text` reaches the model (escaped and attributed to the extension by `formatHarnessNotice`), never its `data`, and `notice` hooks are not offered it.
